1. How I start

Sir, in RoadGuard I did the backend engine. That is the part that decides what happens after a driver presses SOS: how the request is queued and dispatched, how mechanics are matched by skill and distance, how exactly one mechanic wins a job when many accept at the same instant, how the system recovers when a mechanic disappears or nobody accepts, how data is stored, how users are authenticated and authorised, how live updates are pushed, and how the AI photo check is called. I also wrote the REST API and the automated tests.

My friend Sakib did the frontend, which is everything the user sees. Our two parts meet at the REST API and the WebSocket. I provide the endpoints and the pushes, and his pages call them.

I will now go through my part area by area, and say what each file is for.

4. The request lifecycle (state machine)

Every request moves through a finite state machine. The legal moves are stored in an EnumMap<RequestStatus, Set<RequestStatus>> of EnumSets in RequestStatus.java. Every service method asks canTransitionTo() before it changes a status, so a tampered client cannot move a job from searching straight to completed. The rules are enforced on the server.

FromAllowed next states
CREATEDDIAGNOSING, SEARCHING, CANCELLED
DIAGNOSINGSEARCHING, CANCELLED
SEARCHINGOFFERED, ESCALATED, CANCELLED
OFFEREDACCEPTED, SEARCHING, ESCALATED, CANCELLED
ACCEPTEDEN_ROUTE, REASSIGNING, CANCELLED
EN_ROUTEARRIVED, REASSIGNING, CANCELLED
ARRIVEDIN_PROGRESS, REASSIGNING, CANCELLED
IN_PROGRESSCOMPLETED, REASSIGNING, CANCELLED
REASSIGNINGSEARCHING, OFFERED, ACCEPTED, CANCELLED
ESCALATEDSEARCHING, CANCELLED (revived when a mechanic comes back)
COMPLETED, CANCELLEDnone (terminal states)

A mechanic can only push a job to EN_ROUTE, ARRIVED, IN_PROGRESS or COMPLETED (HANDLED_BY_MECHANIC), and only if they are the assigned mechanic. Other moves (offering, accepting, escalating, reassigning) are done by the engine itself. AssignmentService.advanceStatus returns OK, NOT_FOUND, NOT_YOURS or NOT_ALLOWED, which the controller maps to HTTP 200, 404, 403 and 409.

5. Dispatch: queue and worker pool

First, dispatch. When a request is created, its id goes onto an in-memory priority queue, and a pool of worker threads takes requests off the queue and broadcasts offers to mechanics. This is a producer–consumer design: the HTTP thread is the producer and returns immediately, and the workers are the consumers, so a slow dispatch never blocks the driver’s request.

FileLinesWhat it is about
DispatchService.java220The dispatcher. A PriorityBlockingQueue<DispatchTask> and a fixed pool of 4 daemon worker threads (app.dispatch.worker-threads) started in @PostConstruct and stopped in @PreDestroy. Each worker loops on queue.poll(500 ms). DispatchTask is a record implementing Comparable: it orders by Severity.priority() (CRITICAL 0, HIGH 1, MEDIUM 2, LOW 3), then by an AtomicLong sequence number, so equal severities are served in first-in first-out order. broadcast(requestId) runs under the per-request lock inside one transaction: it loads the request, requires status SEARCHING or REASSIGNING, asks MatchingService for candidates, takes the top 3 (5 if the severity is urgent), creates a new offer token, sets OFFERED, saves one RequestOffer row per mechanic, and after the transaction pushes an OFFER message to each mechanic.
RequestService.java362SOS intake and the read side. createSos saves the request as SEARCHING (or DIAGNOSING if a photo is coming) and registers a TransactionSynchronization.afterCommit() callback that calls dispatch.enqueue. Enqueueing after commit matters: a worker could otherwise pick up the id before the row is visible to other transactions.
  • Offer token. ServiceRequest.startNewOfferRound() generates a random UUID and stores it with the set of mechanic ids offered to. A mechanic must send the current token to accept; a token from an earlier round is rejected with OFFER_EXPIRED.
  • Offer audit. Every offer is a RequestOffer row with an OfferOutcome (ACCEPTED, DECLINED, TAKEN, TIMEOUT), so the history of each race is kept.
  • Urgent jobs. HIGH or CRITICAL severity gets 5 offers (app.dispatch.urgent-offer-count) instead of 3, and a 10 km start radius (app.dispatch.urgent-radius-km) instead of 5 km.

6. Matching and ranking

Second, matching. I choose candidates in two stages. Stage one is a cheap database query using a bounding box. Stage two computes the exact distance with the Haversine formula in Java. Then I rank the survivors with a weighted score.

FileLinesWhat it is about
MatchingService.java96findCandidates (read-only transaction) builds the box, runs the query, and calls rank(). rank() drops mechanics with no location, not ONLINE, or farther than the radius by Haversine, splits them into specialists (have the required skill, and the skill is not GENERAL) and generalists, and uses the generalists only if there are no specialists. Score = 0.7 × (distance / radius) + 0.3 × (1 − stars / 5), lower is better. A mechanic with no ratings counts as a neutral 3.5 stars. Ties are broken by profile id so the order is deterministic.
GeoUtils.java45haversineKm (great-circle distance, Earth radius 6371 km, using atan2) and boundingBox: latitude half-width = radius / 111.195 km per degree; longitude half-width = radius / (111.195 × cos(lat)), widened to 180° near the pole to avoid division by zero; latitude is clamped to [−90, 90].
MechanicProfileRepository.java46The JPQL query findCandidatesInBox: status = ONLINE, location not null, latitude and longitude BETWEEN the box, and the mechanic has the skill (:skill MEMBER OF m.specializations) or GENERAL. Also findByStatusInAndLastHeartbeatBefore for the reaper.
  • Why two stages. The box is a square and the radius is a circle, so the SQL pass is a cheap pre-filter and the Haversine pass removes the corners. This avoids computing trigonometry for every mechanic in the table.
  • Why not a routing API. A network call per candidate inside the dispatch path would be slow and may cost money. Cheap maths ranks everyone; a real road route is fetched only in the browser for the one mechanic who accepts.
  • Complexity. Ranking is O(n log n) in the number of candidates inside the box, which is small.

7. The accept race (concurrency control)

Third, the part I consider the core of the project: the accept race. Several mechanics receive the same offer. If they all press Accept at the same millisecond, exactly one must win, and the others must be told cleanly. I solved it with two layers: a per-request fair lock held around a database transaction that commits inside the lock, and optimistic locking with a version column as a backstop.

AssignmentService.accept (simplified) 
ReentrantLock lock = locks.computeIfAbsent(requestId, id -> new ReentrantLock(true));   // one fair lock per request
lock.lock();
try {
    AcceptOutcome outcome = runAccept(requestId, mechanicUserId, offerToken);              // tx.execute(...) commits here
    if (outcome == AcceptOutcome.ACCEPTED) { pushRequest(requestId); realtime.mechanicChanged(mechanicUserId); }
    return outcome;
} finally {
    lock.unlock();
}
/* runAccept: tx.execute(status -> attempt(...)), and OptimisticLockingFailureException -> ALREADY_TAKEN */
FileLinesWhat it is about
AssignmentService.java458The biggest and most important class. It owns every state change of a request that must not race: accept, decline, advanceStatus, cancel, releaseFromMechanic, expireRound, expireSearch, giveUpOnDiagnosing and reviveEscalated. All of them use the same withLock(requestId, ...) helper, so every mutation of one request is serialised, while two different requests never block each other.
AcceptOutcome.java20The result enum: ACCEPTED, ALREADY_TAKEN, OFFER_EXPIRED, NOT_OFFERED_TO_YOU, MECHANIC_NOT_AVAILABLE, REQUEST_NOT_FOUND; isWin() is true only for ACCEPTED.

Why each design choice

  • One lock per request, not one global lock. A global lock (or a synchronized method) would serialise every breakdown in the system. The locks live in a ConcurrentHashMap<Long, ReentrantLock> created with computeIfAbsent, which is atomic.
  • Fair lock (new ReentrantLock(true)): waiting threads get the lock in arrival order instead of arbitrarily, so the first to arrive is the first served.
  • Commit inside the lock. I use TransactionTemplate, not @Transactional. With @Transactional on the method, the lock would be released before Spring commits (the commit happens when the proxy returns), leaving a window where the next thread reads stale data. With tx.execute(...) the transaction has already committed when the lock is released.
  • Optimistic locking backstop. ServiceRequest and MechanicProfile have a @Version column. If the lock were ever bypassed, a second concurrent update would fail with OptimisticLockingFailureException, which I catch and turn into ALREADY_TAKEN.
  • Offer token. Stops a mechanic whose screen is stale from accepting a job that has already moved to a new offer round.

The guards inside one accept attempt (in order)

  1. Request exists, else REQUEST_NOT_FOUND
  2. Status is OFFERED or REASSIGNING, else ALREADY_TAKEN
  3. No mechanic is assigned yet, else ALREADY_TAKEN
  4. The offer token equals the current token, else OFFER_EXPIRED
  5. This mechanic was in the offered set, else NOT_OFFERED_TO_YOU
  6. The state machine allows ACCEPTED, else ALREADY_TAKEN
  7. The mechanic profile is ONLINE, else MECHANIC_NOT_AVAILABLE

On success, in the same transaction: set the assigned mechanic and ACCEPTED with a timestamp, set the mechanic’s profile to BUSY, and resolveOffers marks the winner’s offer row ACCEPTED and every other unanswered offer in the round TAKEN. The controller returns HTTP 200 for the winner and 409 Conflict with won: false for a loser.

What the race test proves, and what it does not. AcceptRaceTest starts 50 threads, holds them on a CountDownLatch and releases them together, 25 times (@RepeatedTest(25)), asserting exactly one ACCEPTED, 49 ALREADY_TAKEN and one accepted offer row. It calls AssignmentService.accept directly on an in-memory H2 database, not through HTTP and not on MariaDB. A ReentrantLock only protects one JVM, so with several server instances the version column would be the only protection (see weak points).

8. Recovery: heartbeats, timeouts, escalation

Fourth, recovery. Real systems fail, so I built three independent safety nets as scheduled background jobs. If a mechanic disappears, the job is released. If nobody accepts, the search radius widens. If nobody is in range, it widens too, and if everything fails the request is escalated.

FileLinesWhat it is about
HeartbeatReaper.java120@Scheduled every 5 seconds. Finds mechanics whose status is ONLINE or BUSY and whose lastHeartbeat is older than 15 seconds (app.heartbeat.timeout-sec). For each one it first marks the mechanic OFFLINE (its own small transaction), then reads the jobs they were holding (ACCEPTED, EN_ROUTE, ARRIVED, IN_PROGRESS) and calls releaseFromMechanic and dispatch.enqueue. The order matters: reversing it would leave a window where a job is attached to a mechanic already known to be gone.
OfferTimeoutService.java188@Scheduled every 20 seconds. sweepOnce() does three things. (1) Requests still OFFERED past the timeout call expireRound: unanswered offers become TIMEOUT, the radius doubles up to a 25 km ceiling, and the request goes back to SEARCHING and is re-queued; after more than 3 attempts it becomes ESCALATED. (2) giveUpOnDiagnosing moves a request whose photo never arrived (30 s) to SEARCHING using the issue type. (3) retryStranded handles SEARCHING or REASSIGNING requests that found nobody in range (they never reached OFFERED), widening them with expireSearch and re-queueing. Separately, reviveEscalated() (not part of the sweep) is called from MechanicService when a mechanic comes back online.
MechanicService.java126Mechanic profile operations: setStatus (rejects BUSY, requires a location before going online, refuses to go online while a job is active), updateLocation (stores position, refreshes the heartbeat, and pushes a MOVED message for every active job of that mechanic), heartbeat and updateSkills (an empty list falls back to GENERAL). When a mechanic comes online, an afterCommit hook calls reviveEscalated() and requeueActiveSearches().

The widening ladder with the default settings, starting at 5 km, attempts limit 3: timeout 1 → 10 km, timeout 2 → 20 km, timeout 3 → 25 km (capped), timeout 4 → ESCALATED. A revived request keeps its widened radius, resets its attempts to zero and is only revived if it was created within the last 30 minutes (app.dispatch.revive-within-sec=1800).

Because the dispatch queue is in memory, a server restart empties it. The 20-second sweep re-enqueues every SEARCHING or REASSIGNING request, and OFFERED requests are found by a database query, so nothing is permanently stranded. Duplicate queue entries are harmless: broadcast skips any request that is not in a dispatchable state.

9. Real-time push (server side)

Fifth, the live updates. The server pushes messages with STOMP over WebSocket and Spring’s simple in-memory broker, so a driver sees status changes and the mechanic moving without refreshing.

FileLinesWhat it is about
WebSocketConfig.java66@EnableWebSocketMessageBroker. Endpoint /ws with SockJS. The simple broker serves /topic and /queue, application prefix /app, user-destination prefix /user. A ChannelInterceptor on the inbound channel inspects the STOMP CONNECT frame, reads the Authorization: Bearer ... native header, validates the JWT through JwtService, and sets the user Principal to the username; a missing or invalid token throws MessageDeliveryException and the connection is refused.
RealtimeNotifier.java111Wraps SimpMessagingTemplate. Message types: OFFER and OFFER_CLOSED (to specific mechanics via convertAndSendToUser(username, "/queue/updates", ...)), STATUS (to /topic/request/{id} and to the assigned mechanic), MOVED (mechanic position, to /topic/request/{id}), MECHANIC (to the mechanic) and a copy of events to /topic/admin. Every send is wrapped in try/catch and logged at debug level, so a failed push never breaks the business transaction.

The simple broker does not store or replay messages, so a client that was disconnected misses them. That is why the frontend also polls every 15 seconds.

  • Mappings. @GeneratedValue(IDENTITY) ids, @Enumerated(EnumType.STRING) for readable and reorder-safe enums, FetchType.LAZY on associations, EAGER only on the two small element collections.
  • Lazy loading and sessions. spring.jpa.open-in-view=false, so lazy associations can only be read inside a transaction. That is why services use @Transactional or TransactionTemplate and DTO from(...) methods run inside them.
  • Repositories. 9 Spring Data interfaces using derived queries (findByStatusAndOfferedAtBefore, findByAssignedMechanicIdAndStatusIn) and one JPQL query. A findByIdForUpdate method with @Lock(PESSIMISTIC_WRITE) exists but is not used anywhere.

  • Images are files, not BLOBs. The database stores only a filename in a varchar(255); the file is under uploads/. This keeps backups and the buffer pool small. The cost is that a file and its row can drift, so the old file is deleted when a photo is replaced.

11. Security

Seventh, security. The API is stateless. A user logs in and receives a JWT. Every later request carries it in the Authorization: Bearer header, and a filter turns it into an authenticated user. Passwords are hashed with BCrypt. Access is controlled twice: by URL rules, and again inside the services by role and ownership checks.

12. AI fault triage (server side)

Eighth, the AI triage. When a driver attaches a photo, the server sends it to a vision model and uses the answer to choose the specialization and severity. The most important design rule is that the AI is advisory: any failure falls back to a safe default, so the AI can never block a rescue.

FileLinesWhat it is about
AiTriageService.java251Provider switch app.ai.provider (stub or gemini); it is live only when the provider is gemini and an API key is set. It posts the image (Base64 inline_data) and the note to the Gemini generateContent REST endpoint with java.net.http.HttpClient, asking for strict JSON: fault category, specialization, severity, confidence, guidance, likely parts. sendWithRetries retries on HTTP 429 and 5xx up to 3 times with a growing delay (800 ms × attempt). parse strips markdown code fences and surrounding chatter (unfence), reads into a record with @JsonIgnoreProperties(ignoreUnknown = true), and falls back field by field when an enum value is unknown (readEnum). Any exception returns fallbackFor(issueType): specialization from the issue type, severity MEDIUM, confidence 0, generic safety guidance, fallback = true.
RequestService.attachPhoto(in 362)Runs in three phases so no database connection is held during the slow network call: (1) a short transaction validates ownership and that the request is still DIAGNOSING; (2) the photo is stored and the AI is called outside any transaction; (3) a second transaction writes the VehicleDiagnosis, sets specialization, severity and radius, moves to SEARCHING, and enqueues dispatch after commit.
UploadRules.java62Shared upload checks: maximum 5 MB, only JPG, PNG or WEBP, and within(directory, name), a path-traversal guard that normalises the path and rejects anything outside the uploads folder.

Severity is only ever set by the AI step. A request without a photo keeps the default MEDIUM.

16. Know these before sir asks

I found these by reading the code. I did not exploit or run any of them, so treat the security ones as “confirmed in the code, not demonstrated”.

1. The password-reset response contains the code. PasswordResetService.initiateReset puts the 6-digit code in the response as codeHint (the comment says “for immediate testing and presentation”). Anyone who knows an account’s email can request a reset, read the code from the response and set a new password. The email step is then pointless. Remove codeHint before any real use. Related: the same service says “No account found with that email address” (reveals which emails exist), has no limit on wrong-code attempts (a 6-digit code has 1,000,000 possibilities) and stores the code in plain text.
2. STOMP subscriptions are not authorised. The interceptor checks the token on CONNECT only. Any logged-in user can subscribe to /topic/request/{id} and receive that request’s status and the mechanic’s live coordinates, and ids are sequential (IDENTITY). /topic/admin is also open to any connected user.
3. The H2 console is exposed. spring.h2.console.enabled=true in application.properties and /h2-console/** is permitAll() in SecurityConfig. Turn it off outside development.
4. The lock is per JVM. A ReentrantLock only works inside one server process. With two instances behind a load balancer, only the @Version check would protect the race. A @Lock(PESSIMISTIC_WRITE) query (findByIdForUpdate) exists but is not used. The locks map also never removes entries, so it grows by one lock per request id for the life of the process.
5. Priority only exists with photos. Severity is set only by the AI step, otherwise every request is MEDIUM, so the queue is effectively first-in first-out, and the 5-offer and 10 km urgent rules apply only to triaged requests.
6. The race test is a service-level test. It does not go through HTTP, does not use MariaDB, and 122 tests do not include controller, security or WebSocket tests.
7. The safe-mode flag cannot be flipped. AssignmentService.safeMode exists, but nothing calls setSafeMode, so the “unsafe mode” comparison demo is not available.
8. No index on the hot columns. The matching query filters on currentLat and currentLng, and sweeps filter on status, but no @Index is declared on those columns. This is fine at demo size, and it means the claim “an index can use the bounding box” is true in principle, not in this schema.
9. Smaller points. GET /api/auth/me is under the public /api/auth/** rule and dereferences the principal, so a missing or invalid token probably gives a 500, not a 401 (I have not run it). JWTs cannot be revoked and logout is client-side only. The HTTPS connector falls back to the keystore password roadguard if none is configured. gemini-3.6-flash in application.properties is a model name I cannot confirm exists; check it before enabling the live AI. The default database is H2; the docs describe MariaDB, so tell sir which one you actually run.

18. How I finish

To summarise, sir: a request enters through the REST API, is queued by priority, matched by skill and distance, offered to several mechanics at once, and exactly one wins because of the per-request lock and the committed transaction. If a mechanic disappears or nobody accepts, scheduled jobs release, widen or escalate the request. Everything is stored in the database, protected by JWT and BCrypt, and pushed live over WebSocket. 122 automated tests cover the engine.

I know the limits: the TCP gateway, fleet simulator, admin dashboard and ratings are not built, and some security points need hardening before real use. Thank you, sir.

19. Possible questions and answers

Answers are written to be said in your own words. A can hand to Sakib tag means the real answer is on the frontend side.

A. Project and architecture

1. What is your part in the project?

The backend engine: dispatch, matching, the accept race, recovery, the state machine, persistence, security, real-time push, the AI triage service, the REST API and the automated tests.

2. What architecture does the backend use?

A layered architecture on Spring Boot: controllers (HTTP and validation), services (business rules and transactions), repositories (Spring Data JPA) and entities. Security and configuration sit alongside. The frontend talks to it through a REST API and a WebSocket.

3. Why Spring Boot?

It gives dependency injection, JPA, security, WebSocket and scheduling in one consistent framework, so I could spend the time on the dispatch and concurrency logic instead of plumbing.

4. Why DTO records and not returning entities?

Entities have lazy associations and internal fields. With open-in-view=false, serialising them outside a transaction would fail, and it would expose fields clients should not see. Records give a stable, minimal contract and are immutable.

5. Which database do you use?

The default configuration is H2 in file mode for development. The MySQL and MariaDB drivers are included, and we select them by overriding the datasource in application-local.properties. Say which one you actually run in the demo. The tests use in-memory H2.

B. Dispatch and matching

6. Why a queue and a worker pool?

It is a producer–consumer design. The HTTP thread only saves the request and puts its id on the queue, so the driver gets an instant response. Four worker threads do the dispatch work in the background, and the number is configurable.

7. Why a priority queue?

So a more serious job is dispatched before a minor one. DispatchTask compares severity first and then an AtomicLong sequence number, so equal severities are first-in first-out. Be honest: severity only comes from the AI step, so without a photo every request is MEDIUM and the queue behaves as FIFO.

8. Why enqueue after the transaction commits?

If I enqueued inside the transaction, a worker could take the id before the row is visible to other transactions and find nothing. TransactionSynchronization.afterCommit() guarantees the data is committed first.

9. How do you choose which mechanics get the offer?

A bounding-box query in the database for online mechanics with the right skill (or GENERAL), then exact Haversine distance in Java to drop those outside the radius, then ranking. Specialists are preferred, and generalists are only used if there is no specialist in range. The top 3 get the offer, or 5 for an urgent job.

10. Explain the ranking formula.

score = 0.7 × (distance / radius) + 0.3 × (1 − rating / 5), lower is better. Distance counts more than rating. An unrated mechanic counts as 3.5 stars so a newcomer is not buried. Ties go to the lower profile id so the order is stable.

11. Why a bounding box before Haversine?

The box is a plain range comparison on two columns, which is cheap and can use an index, whereas Haversine needs trigonometry for every row. The box is a square and the search area is a circle, so the Haversine pass removes the corners. Honest point: I have not declared an index on those columns, so at the moment it is cheap but not indexed.

12. Why not use a routing API for distance?

That would be a network call per candidate inside the dispatch path, slow and possibly paid. Straight-line distance is enough for ranking. The real road route is fetched only in the browser, for the single mechanic who accepts.

13. What is the offer token for?

Each offer round gets a new random UUID. A mechanic must send the current token to accept. A mechanic with a stale screen from an earlier round gets OFFER_EXPIRED instead of taking a job that has moved on.

C. Concurrency (the accept race)

14. What is the race condition here?

Several mechanics get the same offer. If they all press Accept at once, a naive “check status, then assign” could let two threads both see OFFERED and both assign. That is a check-then-act race. Exactly one must win.

15. How do you make exactly one win?

A fair ReentrantLock per request id serialises every accept for that request. Inside the lock I run one database transaction that checks the state, assigns the mechanic and marks the others as taken. The first thread to get the lock wins; later threads see the request already assigned and get ALREADY_TAKEN.

16. Why a lock per request and not synchronized?

A synchronized method (or one global lock) would make every breakdown in the system wait for every other. A per-request lock means two different jobs never block each other. ReentrantLock(true) also gives fairness, which synchronized does not.

17. Why TransactionTemplate and not @Transactional?

With @Transactional on the method, the commit happens when Spring’s proxy returns, which is after the lock was already released. A second thread could then read stale data. TransactionTemplate makes the transaction commit inside the lock, before it is released.

18. If you have a lock, why also a version column?

It is a second line of defence. @Version is optimistic locking: if two transactions read the same row and both try to save, the second fails with OptimisticLockingFailureException, which I turn into ALREADY_TAKEN. It also covers any code path that forgets the lock.

19. Why not rely on the database alone?

Then losers would only learn they lost by catching an exception after doing the work. The lock makes the normal path clean and cheap, and the version check is the safety net.

20. Does your lock work with several servers?

No. A ReentrantLock only exists inside one JVM, so it protects a single-instance deployment. With several instances the @Version check would be the only guard. To scale out I would use a database row lock (a PESSIMISTIC_WRITE query already exists in the repository but is unused) or a distributed lock. The locks map also never removes old entries.

21. How did you test the race?

AcceptRaceTest creates 50 mechanics and one offered request, starts 50 threads that wait on a CountDownLatch, releases them together, and asserts one ACCEPTED and 49 ALREADY_TAKEN. It repeats 25 times, so 1,250 accepts. It calls the service directly on in-memory H2, not through HTTP.

22. What guards run inside an accept?

Request exists, status is OFFERED or REASSIGNING, nobody assigned yet, token matches, the mechanic was offered the job, the state machine allows ACCEPTED, and the mechanic is ONLINE. Each failure returns a specific AcceptOutcome.

D. State machine and persistence

23. How do you enforce legal status changes?

An EnumMap from each status to an EnumSet of allowed next statuses. Every service calls canTransitionTo() before changing state, so illegal moves are refused on the server, whatever the client sends.

24. Why EnumMap and EnumSet?

They are backed by arrays and bit sets indexed by the enum ordinal, so they are fast and compact, and iteration follows the declaration order.

25. What does open-in-view=false do?

It stops Hibernate keeping a session open for the whole web request. Lazy associations can then only be read inside a transaction, which avoids hidden database queries in the view layer and long-held connections. The cost is that DTOs must be built inside transactions.

26. Why are shop and SOS images stored as files?

Binary data in rows makes backups large and competes for database memory. The database keeps only a filename. The trade-off is that a file and its row can get out of step, so I delete the old file when a photo is replaced.

27. What is @ElementCollection used for?

For small sets of simple values without their own entity: the mechanic’s skills and the set of mechanic ids an offer round was sent to. They are stored in their own tables and loaded eagerly because they are small.

28. Some tables are unused. Why?

ratings, event_log and location_updates exist as entities for features we planned (ratings, event replay, location history) but no service or endpoint uses them yet.

E. Recovery

29. What if a mechanic’s phone dies mid-job?

The browser sends a heartbeat or location every 5 seconds. A scheduled reaper runs every 5 seconds and finds mechanics silent for more than 15 seconds. It marks them offline, then releases their jobs to REASSIGNING and re-queues them for dispatch.

30. Why mark the mechanic offline before releasing their jobs?

If I released the jobs first, there would be a window where a job is attached to a mechanic who is already known to be gone, and the mechanic could even accept again. Offline first closes that window.

31. What if nobody accepts?

After 20 seconds the timeout job expires the round: unanswered offers are marked TIMEOUT, the radius doubles up to 25 km, and the request is dispatched again. After more than 3 attempts it becomes ESCALATED. With the defaults that is 5, 10, 20, 25 km, then escalated.

32. What if nobody is in range at all?

Such a request never reaches OFFERED, so the offer timeout alone would not catch it. A separate path (retryStranded) widens requests that are stuck in SEARCHING or REASSIGNING on the same ladder.

33. What happens when a mechanic comes back online?

Giving up was right when nobody was available, but a mechanic coming on duty is new information. So an afterCommit hook revives recently escalated requests (created within 30 minutes), resets their attempts, keeps the widened radius, and re-queues active searches.

34. What if the server restarts? The queue is in memory.

The queue is lost, but all request state is in the database. The 20-second sweep re-enqueues every SEARCHING and REASSIGNING request, and OFFERED requests are found by a query. Duplicates are harmless because broadcast skips anything not in a dispatchable state.

F. Security

35. How does authentication work?

The user logs in and receives a signed JWT. Each request sends it as Authorization: Bearer. JwtAuthenticationFilter validates it, loads the user from the database and sets the security context. The server keeps no session (STATELESS).

36. How are passwords stored?

Hashed with BCrypt (a slow, salted hash) through Spring’s BCryptPasswordEncoder. Plain passwords are never stored. Login returns the same error for a wrong email and a wrong password.

37. Why is CSRF disabled?

CSRF attacks rely on the browser automatically sending a cookie. This API uses a Bearer token that the page adds itself, and no session cookie, so the classic CSRF attack does not apply. The trade-off is that the token lives in the browser’s local storage, which depends on the frontend preventing XSS.

38. How do you control who can do what?

Two layers. URL rules in SecurityConfig (/api/mechanic/** needs the mechanic role, /api/admin/** needs admin). Then service-level checks: only a driver can send or cancel an SOS, only a mechanic can accept, and canView allows only the driver, the assigned mechanic or an admin to read a request.

39. Can someone register as an admin?

No. register rejects the ADMIN role. The first admin is created at startup by AdminSeeder from the git-ignored local properties.

40. How does the WebSocket know who is connected?

A channel interceptor reads the Authorization header in the STOMP CONNECT frame, validates the JWT, and sets the user principal. A missing or bad token refuses the connection. The principal name is the username, which is how convertAndSendToUser targets one user.

41. Is the password reset secure?

Not as it stands. The code is generated with SecureRandom, expires in 15 minutes and is single-use, which is good. But the response also returns the code (codeHint, there for testing and presentation), so anyone with an email address could reset that account. It also reveals which emails exist and has no limit on wrong guesses. I would remove codeHint, return a generic message, and limit attempts before real use.

42. Are WebSocket topics protected?

Only the connection is authenticated. I do not authorise individual subscriptions, so a logged-in user who guesses a request id could subscribe to /topic/request/{id}. The fix is a SUBSCRIBE interceptor that checks the user may view that request.

43. Why is the H2 console open?

It was kept for development convenience. It should be disabled for anything but local use, because it exposes the database.

G. AI, API and tests

44. How does the AI triage work?

The photo and the note are sent to the Gemini REST API with a prompt asking for strict JSON (fault category, specialization, severity, confidence, guidance, parts). The answer is parsed defensively and used to set the required specialization, severity and search radius. The call retries on 429 and 5xx and has timeouts.

45. What if the AI fails or gives garbage?

Any exception, timeout or unreadable answer returns a fallback built from the issue type the driver picked, with severity MEDIUM and a generic safety tip. An unknown enum value only replaces that one field. A request whose photo never arrives is moved on after 30 seconds. The AI can never block a rescue.

46. How accurate is the AI?

We have not measured its accuracy, so I cannot give a number. The default provider setting is stub, so unless a Gemini key is configured the app uses the fallback. Check which mode your demo is in before you say anything about it.

47. Why three phases in attachPhoto?

The AI call is slow and goes over the network. If it ran inside a transaction it would hold a database connection for seconds. So I validate in a short transaction, call the AI outside any transaction, then write the result in a second short transaction.

48. How do you validate input?

Bean Validation annotations on the request records, enforced by @Valid in the controllers: not-null, size limits, latitude and longitude ranges, email format, a phone-number pattern. A failure becomes a 400 with the first field error. File uploads are limited to 5 MB and JPG, PNG or WEBP, and paths are normalised so a file cannot escape the uploads folder.

49. How are errors returned to the client?

One @RestControllerAdvice maps exceptions to a JSON body {status, error, message}: 400 for bad input, 401 for bad credentials, 403 for access denied, 409 for conflicts. A lost accept returns 409 with won: false.

50. What do your 122 tests cover, and what do they miss?

They are integration tests on the real Spring context with in-memory H2: the accept race, heartbeat recovery, timeouts and escalation, revival, matching, lifecycle rules, skills, AI parsing and triage dispatch. They do not test controllers over HTTP, security rules, WebSocket messages or MariaDB.

H. Hard questions

51. What is not finished?

The raw TCP gateway (the port is configured but no server exists), the fleet simulator, the admin API and dashboard, the unsafe-mode toggle, the ratings flow and event replay. Some security points also need hardening: the reset code in the response, subscription authorisation and the H2 console.

52. How would you scale this to many servers?

Replace the in-JVM lock with a database row lock or a distributed lock, move the dispatch queue to a shared broker, use an external message broker for WebSocket instead of the in-memory simple broker, add indexes on the location and status columns, and use proper schema migrations instead of ddl-auto=update.
