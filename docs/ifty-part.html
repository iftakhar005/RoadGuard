1. How I start

Sir, in RoadGuard I did the backend engine. That is the part that decides what happens after a driver presses SOS: how the request is queued and dispatched, how mechanics are matched by skill and distance, how exactly one mechanic wins a job when many accept at the same instant, and how the system recovers when a mechanic disappears or nobody accepts.

I also built the raw TCP device gateway on port 9090, which is our socket-programming component, and a fleet simulator that opens many real sockets so the system can be demonstrated and tested without real phones. On top of that I built ratings, an event log with replay, driver–mechanic chat, a nearby-mechanics endpoint and the admin dashboard API. Everything is stored with JPA, protected by JWT and BCrypt, pushed live over WebSocket, and covered by over 1,100 automated tests, including an accept race repeated 1,000 times.

My friend Sakib did the frontend. Our two parts meet at the REST API and the WebSocket: I provide the endpoints and the pushes, and his pages call them.

I will now go through my part area by area, and say what each file is for.

4. The request lifecycle (state machine)

Every request moves through a finite state machine. The legal moves are stored in an EnumMap<RequestStatus, Set<RequestStatus>> of EnumSets in RequestStatus.java. Every service asks canTransitionTo() before changing a status, so a tampered client cannot move a job from searching straight to completed.

FromAllowed next states
CREATEDDIAGNOSING, SEARCHING, CANCELLED
DIAGNOSINGSEARCHING, CANCELLED
SEARCHINGOFFERED, ESCALATED, CANCELLED
OFFEREDACCEPTED, SEARCHING, ESCALATED, CANCELLED
ACCEPTEDEN_ROUTE, REASSIGNING, CANCELLED
EN_ROUTEARRIVED, REASSIGNING, CANCELLED
ARRIVEDIN_PROGRESS, REASSIGNING, CANCELLED
IN_PROGRESSCOMPLETED, REASSIGNING, CANCELLED
REASSIGNINGSEARCHING, OFFERED, ACCEPTED, CANCELLED
ESCALATEDSEARCHING, CANCELLED (revived when a mechanic comes back)
COMPLETED, CANCELLEDnone (terminal)

A mechanic can only push a job to EN_ROUTE, ARRIVED, IN_PROGRESS or COMPLETED, and only if they are the assigned mechanic. advanceStatus returns OK, NOT_FOUND, NOT_YOURS or NOT_ALLOWED, which the controller maps to HTTP 200, 404, 403 and 409. The same method is used by the REST API and by the TCP gateway.

5. Dispatch: queue and worker pool

First, dispatch. When a request is created, its id goes onto an in-memory priority queue, and a pool of worker threads takes requests off it and broadcasts offers. This is a producer–consumer design: the HTTP thread returns immediately, and the workers do the slow part in the background.

FileLinesWhat it is about
DispatchService.java220A PriorityBlockingQueue<DispatchTask> and a fixed pool of 4 daemon worker threads (app.dispatch.worker-threads), started in @PostConstruct. Each worker loops on queue.poll(500 ms). DispatchTask implements Comparable: by Severity.priority() (CRITICAL 0, HIGH 1, MEDIUM 2, LOW 3), then an AtomicLong sequence number, so equal severities are first-in first-out. broadcast(requestId) runs under the per-request lock inside one transaction: it requires status SEARCHING or REASSIGNING, gets candidates from MatchingService, takes the top 3 (5 if urgent), creates a new offer token, sets OFFERED, saves one RequestOffer row per mechanic, and afterwards notifies each mechanic.
RequestService.java403SOS intake and reads. createSos saves the request and registers a TransactionSynchronization.afterCommit() callback that calls dispatch.enqueue; enqueueing after commit stops a worker from picking up an id whose row is not yet visible. Also photo handling and AI triage (section 18), chat and rating endpoints, and the replay endpoint.
  • Offer token. startNewOfferRound() generates a random UUID and stores it with the set of offered mechanic ids. Accepting needs the current token, so a stale one gets OFFER_EXPIRED.
  • Offer audit. Every offer is a RequestOffer row with an OfferOutcome (ACCEPTED, DECLINED, TAKEN, TIMEOUT).
  • Urgent jobs. HIGH or CRITICAL severity gets 5 offers instead of 3 and a 10 km start radius instead of 5 km.
  • Wider races on demand. app.dispatch.offer-count can be raised (the example config has #app.dispatch.offer-count=10 for a wide race demo).

6. Matching, ranking and nearby mechanics

Second, matching. I choose candidates in two stages: a cheap database query using a bounding box, then exact distance with the Haversine formula in Java, then a weighted score.

FileLinesWhat it is about
MatchingService.java96findCandidates builds the box, runs the query, and rank() drops mechanics with no location, not ONLINE, or beyond the radius, splits them into specialists and generalists, and uses generalists only if there are no specialists. Score = 0.7 × (distance / radius) + 0.3 × (1 − stars / 5), lower is better; unrated counts as 3.5 stars; ties by profile id. Ratings now come from real driver ratings (section 13).
GeoUtils.java45haversineKm (Earth radius 6371 km, atan2) and boundingBox (latitude half-width = radius / 111.195; longitude scaled by 1/cos(lat), widened to 180° near the pole).
NearbyMechanicService.java NEW49“Who could a driver call right now?” The same pool the dispatcher draws from, without the skill filter: online mechanics within a radius (default 10 km, capped at 50 km, at most 40 results), nearest first. The response does not include account ids or phone numbers. Exposed as GET /api/mechanics/nearby.
  • Why two stages. The box is a square and the radius a circle, so SQL is a cheap pre-filter and Haversine removes the corners.
  • Why not a routing API. A network call per candidate in the dispatch path would be slow and may cost money; the real road route is fetched in the browser for the one mechanic who accepts.

7. The accept race (concurrency control)

Third, the core of the project: the accept race. Several mechanics receive the same offer, and if they all accept at the same millisecond exactly one must win. I used a per-request fair lock around a database transaction that commits inside the lock, with optimistic locking (a version column) as a backstop. It is proven by a test that races 50 mechanics, 1,000 times.

AssignmentService.accept (simplified) 
if (!safeMode) { return runAccept(requestId, mechanicUserId, offerToken); }          // demo switch: lock off

ReentrantLock lock = locks.computeIfAbsent(requestId, id -> new ReentrantLock(true)); // one fair lock per request
lock.lock();
try {
    AcceptOutcome outcome = runAccept(requestId, mechanicUserId, offerToken);          // tx.execute(...) commits here
    if (outcome == AcceptOutcome.ACCEPTED) { pushRequest(requestId); realtime.mechanicChanged(mechanicUserId); }
    return outcome;
} finally {
    lock.unlock();
}
FileLinesWhat it is about
AssignmentService.java458Owns every state change of a request that must not race: accept, decline, advanceStatus, cancel, releaseFromMechanic, expireRound, expireSearch, giveUpOnDiagnosing, reviveEscalated. All use the same withLock helper, so one request is serialised while different requests never block each other.
AcceptOutcome.java20ACCEPTED, ALREADY_TAKEN, OFFER_EXPIRED, NOT_OFFERED_TO_YOU, MECHANIC_NOT_AVAILABLE, REQUEST_NOT_FOUND.

Why each design choice

  • One lock per request. A global lock or synchronized method would serialise every breakdown. Locks live in a ConcurrentHashMap created with the atomic computeIfAbsent.
  • Fair lock (new ReentrantLock(true)): threads get the lock in arrival order.
  • Commit inside the lock. TransactionTemplate, not @Transactional: with the annotation the commit happens after the method returns, i.e. after the lock is released, leaving a stale-read window.
  • Optimistic locking backstop. @Version on ServiceRequest and MechanicProfile; a lost update throws OptimisticLockingFailureException, which is turned into ALREADY_TAKEN.
  • Offer token stops a stale screen from taking a job that moved on.

Guards inside one accept attempt (in order)

  1. Request exists, else REQUEST_NOT_FOUND
  2. Status is OFFERED or REASSIGNING, else ALREADY_TAKEN
  3. No mechanic assigned yet, else ALREADY_TAKEN
  4. Offer token matches the current one, else OFFER_EXPIRED
  5. This mechanic was offered the job, else NOT_OFFERED_TO_YOU
  6. The state machine allows ACCEPTED, else ALREADY_TAKEN
  7. The mechanic profile is ONLINE, else MECHANIC_NOT_AVAILABLE

On success, in one transaction: set assigned mechanic and ACCEPTED, set the mechanic BUSY, and mark the winner’s offer ACCEPTED and every other unanswered offer in the round TAKEN. The REST controller returns 200 for the winner and 409 Conflict with won: false for a loser.

The demo switch (“safe mode”). AssignmentService still has safeMode, and the admin API can switch the lock off (POST /api/admin/safe-mode, allowed while app.demo.allow-unsafe is true, which is its default). The commit message of 18c889e says “remove safeMode checks”, but the check in accept is still there. In my test run, turning the lock off did not produce a double winner (test raceWithLockOffProducesMultipleWinners failed twice: “unsafe mode should produce a collision in 50 tries”). My interpretation, which I have not proven: the transaction and @Version check alone still stopped a second winner on H2. Do not promise a live “collision” demo.
What the race test proves, and what it does not. AcceptRaceTest holds 50 threads on a CountDownLatch, releases them together, and repeats 1,000 times (@RepeatedTest(1000)), asserting exactly one ACCEPTED, 49 ALREADY_TAKEN and one accepted offer row. It calls the service directly on in-memory H2 (see also the TCP race in section 10, which goes through real sockets). A ReentrantLock only protects one JVM.

8. Recovery: heartbeats, timeouts, escalation

Fourth, recovery. I built safety nets as scheduled background jobs: if a mechanic disappears the job is released, if nobody accepts the search radius widens, and if everything fails the request is escalated.

FileLinesWhat it is about
HeartbeatReaper.java120@Scheduled every 5 s. Mechanics ONLINE or BUSY with a heartbeat older than 15 s (app.heartbeat.timeout-sec): first marked OFFLINE, then their held jobs (ACCEPTED, EN_ROUTE, ARRIVED, IN_PROGRESS) are released with releaseFromMechanic and re-queued. Reversing the order would leave a job attached to a mechanic already known to be gone.
OfferTimeoutService.java188@Scheduled every 20 s. sweepOnce() (1) expires rounds still OFFERED past the timeout: unanswered offers become TIMEOUT, the radius doubles to a 25 km ceiling and the request is re-queued; after more than 3 attempts it becomes ESCALATED; (2) moves a request whose photo never arrived (30 s) on to SEARCHING; (3) retryStranded widens SEARCHING/REASSIGNING requests that found nobody in range. Separately, reviveEscalated() is called when a mechanic comes back online.
MechanicService.java130setStatus (rejects BUSY, needs a location to go online), updateLocation (saves position, refreshes the heartbeat, pushes MOVED and records a location event for every active job), heartbeat, updateSkills (empty falls back to GENERAL). Coming online triggers revival and re-queueing after commit.

Ladder with defaults (start 5 km, attempts limit 3): timeout 1 → 10 km, 2 → 20 km, 3 → 25 km (capped), 4 → ESCALATED. A revived request keeps its widened radius, resets attempts to zero, and is only revived if created within 30 minutes. The queue is in memory, so a restart empties it; the 20-second sweep re-enqueues every SEARCHING/REASSIGNING request and finds OFFERED ones by query, and duplicate entries are harmless because broadcast skips non-dispatchable states.

10. The raw TCP device gateway NEW

Sixth, our socket-programming component: a gateway on TCP port 9090 for devices that cannot speak HTTP, such as a tracker in a tow truck. It is a plain ServerSocket with a line-based text protocol and a persistent connection per device. It is only another way in: every command goes to the same services the browser uses, so a mechanic on a socket and a mechanic in a browser race for a job on equal terms.

FileLinesWhat it is about
TcpGateway.java432Opens a ServerSocket on app.tcp.port (9090) in @PostConstruct (set app.tcp.enabled=false to disable). An acceptor thread loops on accept() and hands each connection to a fixed pool of 64 worker threads (app.tcp.workers); one worker serves one connection for its whole life, blocking on readLine() (thread-per-connection with a bounded pool). A ConcurrentHashMap of sessions by mechanic id lets the server push to an open socket; writes are synchronized. @EventListener methods turn Spring events into lines: OFFER, TAKEN, ASSIGNED. When a socket closes, the mechanic is marked offline.
OffersSentEvent, OfferClosedEvent, RequestAssignedEvent6 / 6 / 4Small records published by RealtimeNotifier and consumed by the gateway, so the dispatch code does not depend on sockets.

  • Why a raw socket. HTTP is one request and one response. A device that must receive jobs the instant they appear needs a persistent connection the server can push down. A browser cannot open a raw TCP socket, so only a device or the simulator uses this path.
  • Tested. TcpGatewayTest (17 tests, real sockets): good, fake and borrowed tokens; hello-first rule; positions saved and nonsense coordinates refused; offers, “taken” and “won” reach the socket; hanging up takes the mechanic off duty; devices racing down sockets still produce exactly one winner; a location over the socket pushes MOVED; a job can go from accepted to completed over the socket; stages cannot be skipped; a mechanic cannot move someone else’s job.

11. The fleet simulator NEW

Seventh, the fleet simulator. It puts pretend mechanics on the road, each holding its own real TCP connection to the gateway, so the dispatcher has something to dispatch to and the accept race can be run for real instead of described. It runs from the admin page or from the command line.

FileLinesWhat it is about

sim/FleetRunner.java283The engine. Opens one VirtualMechanic per account on a cached thread pool, runs a 2-thread ScheduledExecutorService as the clock (position tick every 3 s), tallies outcomes, keeps a 40-line “story” of what happened, and handles race mode: every mechanic offered the same job waits on one CountDownLatch released after a 600 ms grace period, then all answer ACCEPT at the same instant. 17. Security

Eleventh, security. The API is stateless: a user logs in, receives a JWT, and a filter turns it into an authenticated user on every request. Passwords are hashed with BCrypt. Access is checked twice: by URL rules, and again inside the services by role and ownership.

22. Know these before sir asks

I found these by reading the code at 18c889e and running its tests. I did not exploit or run any of the security points, so treat them as “confirmed in the code, not demonstrated”.

1. The newest commits do not build. See the red box at the top. The last commit that builds and has everything is 18c889e.
2. The password-reset response contains the code. PasswordResetService.initiateReset returns the 6-digit code as codeHint (“for immediate testing and presentation”). Anyone who knows an email can request a reset, read the code and set a new password. The same service also says “No account found” (reveals which emails exist), has no limit on wrong guesses, and stores the code in plain text. This file did not change in the new commits.
3. STOMP subscriptions are not authorised. The interceptor checks the token on CONNECT only. Any logged-in user could subscribe to /topic/request/{id} (status and live coordinates, with sequential ids), /topic/chat/{id} (a job’s private chat) or /topic/admin. The REST chat endpoints do check membership, so the topic is the leak.
4. Simulator accounts have a known password. sim_mech_1…25 use the fixed password fleet-sim-pass, have every skill, and are never deleted. On any server that other people can reach, anyone could log in as them.
5. The H2 console and the lock switch. /h2-console/** is public in SecurityConfig (the console is enabled in application.properties), and app.demo.allow-unsafe defaults to true, so an admin can turn the accept lock off through the API. Turn both off outside demos.
6. The lock is per JVM. A ReentrantLock only works inside one server process; with several instances only the @Version check protects the race. The locks map never removes entries (one lock per request id for the life of the process).
7. Priority only exists with photos. Severity is set only by the AI step; otherwise every request is MEDIUM, the queue is first-in first-out, and the 5-offer and 10 km urgent rules apply only to triaged requests.
8. The TCP gateway is plain text. The login token travels unencrypted; there is no TLS on port 9090, no read timeout, and each connection holds a worker, so more than 64 simultaneous connections would wait. The listener binds to all interfaces (0.0.0.0).
9. Replay and logging details. Snapshots use Java serialization and are read back with ObjectInputStream, which is only safe because only the server writes those files. Logs and snapshots grow without rotation. Each location sample (at most one per 2 s per job) costs extra database and file writes.
10. Smaller points. No index on mechanic position or request status. GET /api/auth/me with no valid token probably returns 500, not 401 (I have not run it). JWTs cannot be revoked, and logout is client-side. The HTTPS connector falls back to the keystore password roadguard. gemini-3.6-flash in application.properties is a model name I cannot confirm exists. The race test and the gateway tests run on in-memory H2, not on MySQL/MariaDB.

25. Possible questions and answers

Answers are written to be said in your own words. A can hand to Sakib tag means the real answer is on the frontend side.

A. Project and architecture

1. What is your part in the project?

The backend engine: dispatch, matching, the accept race, recovery, the state machine, persistence, security, the TCP gateway and fleet simulator, ratings, event replay, chat, the admin API, the REST API and the automated tests.

2. What architecture does the backend use?

A layered architecture on Spring Boot: controllers, services, repositories and entities, with security and configuration alongside. There are two entrances, REST/WebSocket for browsers and a raw TCP gateway for devices, and both go to the same services.

3. Why DTO records and not entities?

Entities have lazy associations and internal fields. With open-in-view=false, serialising them outside a transaction would fail, and it would expose fields clients should not see. Records give a stable, minimal, immutable contract.

4. Which database do you use?

Real data lives in MySQL or MariaDB, configured in the git-ignored application-local.properties. The app refuses to start on the throwaway H2 database unless app.db.allow-throwaway=true. The automated tests use in-memory H2. Say which one your demo uses.

5. Why does the app refuse to start on H2?

A missing local settings file used to leave the app on an empty H2 file with nothing in the log, so every account seemed to vanish and password recovery said the account did not exist. DatabaseCheck prints which database was opened and stops instead of running on the wrong one.

B. Dispatch and matching

6. Why a queue and a worker pool?

It is a producer–consumer design. The HTTP thread saves the request and puts its id on the queue so the driver gets an instant response; four worker threads do the dispatch in the background.

7. Why a priority queue?

So a more serious job is dispatched first. Tasks compare severity, then an AtomicLong sequence number, so equal severities are first-in first-out. Be honest: severity only comes from the AI step, so without a photo everything is MEDIUM and the queue behaves as FIFO.

8. Why enqueue after the transaction commits?

Otherwise a worker could take the id before the row is visible to other transactions and find nothing. afterCommit() guarantees the data is committed first.

9. How do you choose which mechanics get an offer?

A bounding-box query for online mechanics with the right skill (or GENERAL), then exact Haversine distance to drop those outside the radius, then ranking. Specialists first; generalists only if there is no specialist. The top 3 get the offer (5 if urgent).

10. Explain the ranking formula.

score = 0.7 × (distance / radius) + 0.3 × (1 − rating / 5), lower is better. Distance counts more than rating. An unrated mechanic counts as 3.5 stars so a newcomer is not buried. Ratings now come from real driver ratings that recompute the mechanic’s average.

11. Why a bounding box before Haversine?

The box is a plain range check on two columns, which is cheap, whereas Haversine needs trigonometry for every row. The box is a square and the search area a circle, so Haversine removes the corners. Honest point: I have not declared an index on those columns.

12. What is the offer token for?

Each offer round gets a new random UUID. A mechanic must send the current token to accept, so one with a stale screen gets OFFER_EXPIRED instead of taking a job that moved on.

13. Who decides the trade, the driver or the AI?

The driver. Unless the driver picked “Other”, the issue they chose decides the specialization. The model only names the trade when the driver left it open. What the model thought is kept and shown as guidance. The reason: a photo of an open bonnet looks the same whether the tank is empty or the engine is boiling.

C. Concurrency (the accept race)

14. What is the race condition?

Several mechanics get the same offer. A naive “check status, then assign” could let two threads both see OFFERED and both assign. That is a check-then-act race. Exactly one must win.

15. How do you make exactly one win?

A fair ReentrantLock per request id serialises every accept for that request. Inside it I run one transaction that checks the state, assigns the mechanic and marks the others as taken. The first thread to get the lock wins; later ones see the request already assigned and get ALREADY_TAKEN.

16. Why a lock per request and not synchronized?

synchronized or a global lock would make every breakdown wait for every other. A per-request lock means different jobs never block each other, and ReentrantLock(true) adds fairness.

17. Why TransactionTemplate and not @Transactional?

With @Transactional the commit happens when Spring’s proxy returns, after the lock was released, so the next thread could read stale data. TransactionTemplate commits inside the lock.

18. If you have a lock, why also a version column?

It is a second line of defence. @Version is optimistic locking: if two transactions read the same row and both save, the second fails with OptimisticLockingFailureException, which I turn into ALREADY_TAKEN.

19. Does your lock work with several servers?

No. A ReentrantLock exists only inside one JVM. With several instances only the version check would protect the race. To scale out I would use a database row lock (a PESSIMISTIC_WRITE query exists but is unused) or a distributed lock.

20. How did you test the race?

AcceptRaceTest creates 50 mechanics and one offered request, starts 50 threads waiting on a CountDownLatch, releases them together and asserts one winner and 49 ALREADY_TAKEN. It repeats 1,000 times, so 50,000 accepts. TcpGatewayTest repeats the idea with real sockets.

21. What does the “lock off” switch do, and why did its test fail?

It makes accept skip the lock so you can compare. The test raceWithLockOffProducesMultipleWinners expects a double winner within 50 tries; in my runs there was none. My interpretation, not proven, is that the transaction and the @Version check still stopped a second winner on H2, which would show the backstop works. It means the live “break it” demo is unreliable.

D. State machine and persistence

22. How do you enforce legal status changes?

An EnumMap from each status to an EnumSet of allowed next statuses. Every service calls canTransitionTo() first, so illegal moves are refused on the server whatever the client sends.

23. What does open-in-view=false do?

It stops Hibernate keeping a session open for the whole web request, so lazy associations can only be read inside a transaction. That avoids hidden queries in the view layer and long-held connections. The cost is that DTOs must be built inside transactions.

24. Why are images stored as files?

Binary data in rows makes backups large and competes for database memory. The database keeps only a filename. The trade-off is that a file and its row can drift. Chat images get a random UUID name and a path-traversal guard.

E. Recovery

25. What if a mechanic’s phone dies mid-job?

The page sends a heartbeat or position every 5 seconds. The reaper runs every 5 seconds and finds mechanics silent for more than 15. It marks them offline, then releases their jobs to REASSIGNING and re-queues them.

26. Why mark the mechanic offline before releasing their jobs?

Otherwise there is a window where a job is attached to a mechanic already known to be gone, who could even accept again. Offline first closes it.

27. What if nobody accepts, or nobody is in range?

After 20 seconds the offer round expires, unanswered offers become TIMEOUT, the radius doubles up to 25 km and the request is dispatched again; after more than 3 attempts it is escalated. A request with nobody in range never reaches OFFERED, so a separate sweep widens it on the same ladder.

28. What if the server restarts and the queue is lost?

All request state is in the database. The 20-second sweep re-enqueues every SEARCHING and REASSIGNING request, and OFFERED ones are found by a query. Duplicates are harmless because broadcast skips anything not dispatchable.

F. The TCP gateway and the simulator

29. What is the socket-programming part?

The device gateway on TCP port 9090. A ServerSocket accepts connections, a pool of 64 worker threads serves them, one worker per connection, with a line-based text protocol (HELLO, LOC, ACCEPT, STATUS…). The server can push offers down an open connection.

30. Why raw TCP when you already have HTTP?

HTTP is one request and one reply. A device like a tow-truck tracker needs a persistent connection to receive jobs the moment they appear. A browser cannot open a raw TCP socket, so this path is for devices and the simulator.

31. How does the gateway authenticate a device?

The first line must be HELLO <mechanicId> <jwt>. The server validates the JWT, checks that the token belongs to that id and that the user is a mechanic, and refuses anything else with AUTH_FAIL. Before HELLO, every command gets ERR say HELLO first. The weakness: no TLS, so the token travels in plain text.

32. Is a mechanic on a socket treated differently from one in a browser?

No. The gateway calls the same AssignmentService.accept, advanceStatus and MechanicService methods. They race on equal terms, and a test with devices racing down sockets still produces exactly one winner.

33. What is the fleet simulator for?

To demonstrate and test with many mechanics without many phones. Each pretend mechanic opens its own real socket, receives pushed offers and answers. In race mode they all accept at once, and one wins. The winner then drives to the driver, sending positions, and completes the job. “Drop winner” shows recovery.

34. Why does the registered-mechanic count keep growing?

The simulator creates real accounts named sim_mech_N and reuses them, so the count only grows when you raise the fleet size (maximum 25). They are never deleted, and the database is persistent.

35. What does the Race switch do?

It decides when the pretend mechanics answer: staggered after a random think time, or all at the same instant after a 600 ms gathering delay. It does not turn off the server’s lock. The race is only as wide as offer-count (3 by default).

36. How would you prove the sockets are real?

Run netstat -an | findstr 9090 while the fleet runs: one LISTENING line and 16 ESTABLISHED lines for 8 mechanics (each connection appears from both ends). Stop the fleet and they disappear. The story panel also prints the raw protocol lines.

G. Replay, ratings and chat

37. How does the replay work?

Every event of a job (offers, status changes, location samples) is saved to a database table and to a JSON Lines file. When the job completes or is cancelled, a timeline snapshot is written with Java serialization. The replay endpoint returns the snapshot, or rebuilds the timeline from the log, and only the driver, the assigned mechanic or an admin may read it.

38. Why throttle location samples?

A mechanic reports every few seconds, and every sample would cost database and file writes. Recording at most one sample per request per 2 seconds keeps the path accurate enough and the writes small.

39. How do ratings work?

Only the driver of a COMPLETED request can rate it, once, with 1–5 stars. The check is in code and also enforced by a unique database constraint, so two simultaneous ratings cannot both succeed. Then the mechanic’s average is recomputed and the matcher uses it.

40. How does chat stay private?

Chat is only open while a mechanic is assigned and the job is active, and only that job’s driver and mechanic can write or read through the REST endpoints. Images are checked by a strict pattern and size, stored as files with random names, and fetched through an authorised endpoint. Weakness: messages are also broadcast on /topic/chat/{id}, and WebSocket subscriptions are not authorised.

H. Security

41. How does authentication work?

Login returns a signed JWT sent as Authorization: Bearer. JwtAuthenticationFilter validates it, loads the user from the database and sets the security context. The server keeps no session (STATELESS).

42. How are passwords stored?

Hashed with BCrypt (slow and salted). Plain passwords are never stored. Login returns the same error for a wrong email and a wrong password.

43. Why is CSRF disabled?

CSRF relies on the browser automatically sending a cookie. This API uses a Bearer token the page adds itself and no session cookie, so the classic attack does not apply. The trade-off is that the token lives in the browser’s local storage.

44. How do you control who can do what?

Two layers: URL rules in SecurityConfig (mechanic and admin areas), then service-level checks on role and ownership: only a driver can send or cancel an SOS, only a mechanic can accept, and only the people on a job (or an admin) can read its photo, chat, replay or rating.

45. Is the password reset secure?

Not as it stands. The code is random, expires in 15 minutes and is single-use, which is good. But the response also returns it (codeHint, there for testing and presentation), so anyone with an email could reset that account. It also reveals which emails exist and has no limit on wrong guesses. I would remove codeHint and limit attempts before real use.

46. Are WebSocket topics protected?

Only the connection is authenticated, not each subscription. A logged-in user who guesses a request id could subscribe to /topic/request/{id} or /topic/chat/{id}. The fix is a SUBSCRIBE interceptor that checks the user may view that request.

47. Are the simulator accounts a risk?

Yes, on a shared server: they share the fixed password fleet-sim-pass. For a real deployment I would delete them, or generate random passwords, and keep the simulator off.

I. AI, API and tests

48. How does the AI triage work, and what if it fails?

The photo and note go to the Gemini REST API with a prompt asking for strict JSON. The answer is parsed defensively and used for guidance and severity. Any exception, timeout or unreadable answer returns a fallback from the issue type. The driver’s choice decides the trade, so the AI can never block or misroute a rescue. A request whose photo never arrives moves on after 30 seconds.

49. How accurate is the AI?

We have not measured its accuracy, so I cannot give a number. The default provider is stub, so unless a Gemini key is configured the app uses the fallback. Check which mode your demo is in.

50. How do you validate input and report errors?

Bean Validation annotations on the request records enforced by @Valid: not-null, size limits, coordinate ranges, email format, phone pattern. One @RestControllerAdvice maps exceptions to a JSON body {status, error, message}: 400, 401, 403, 409. Uploads are limited to 5 MB and JPG, PNG or WEBP, and paths are normalised so a file cannot escape the uploads folder.

51. What do your tests cover, and what do they miss?

Over 1,100 integration tests on the real Spring context: the race (1,000 repetitions), recovery, matching, lifecycle, the TCP gateway with real sockets, ratings, chat, replay, admin and triage routing. They do not test controllers over HTTP, URL security rules, WebSocket subscriptions or MySQL. Also, 2 tests in FleetControlTest currently fail.

52. How do you know live tracking works?

A location sent over the browser or the socket is saved, and a MOVED message with latitude and longitude is pushed to /topic/request/{id}. There is a test for it (“a location report over the socket pushes moved to whoever is waiting”), the messages are visible in the browser’s WebSocket tab, and the simulator’s winner sends a position every second. The simulator moves in a straight line, not along roads.
