RoadGuard: Team Split

CSE 2118 · Advanced Object-Oriented Programming Lab · Final presentation

The one-sentence pitch. A driver breaks down and presses one button. Every qualified mechanic nearby is alerted at the same time, the first to accept gets the job, and the rest are told it is taken. The hard part is correctness under concurrency: when several mechanics accept in the same millisecond, exactly one must win.

Likely questions, and who answers

Why a lock per request rather than synchronized? — Ifty

A synchronized method on the service would serialise every breakdown in the system. Per-request locks mean two different jobs never block each other, and ReentrantLock also gives fairness, which synchronized does not.

Why not rely on the database alone? — Ifty

We keep version checking as a backstop. Relying on it alone means losers discover they lost by catching an exception after doing the work. The lock makes the common path clean and cheap.

Why commit inside the lock? — Ifty

With @Transactional the lock would release before the commit landed, leaving a window where a second thread reads stale data. We use TransactionTemplate so the commit happens inside the lock.

What happens if the mechanic's phone dies? — Ifty

Fifteen seconds of missed heartbeats and the reaper marks the mechanic offline, then releases and re-dispatches the job.

What if the AI is wrong or down? — Ifty

The AI is advisory. On any failure the specialization comes from the issue type the driver picked, severity is medium, and the guidance is a generic safety message. A request stuck waiting for the photo moves on after 30 seconds. We have not measured the AI's accuracy, so we make no accuracy claim.

Why not just use Google Maps? — Sakib

Google Maps shows where things are. It does not decide who gets the job when several mechanics accept at once. The map is a library we call; dispatch is what we built. We use OpenStreetMap and OSRM, which need no API key.

How does the driver see the mechanic move so fast? — Sakib

The server publishes each position to that job's WebSocket topic and the page moves the marker from the message with no refetch. The route and ETA are throttled separately so we do not hammer the routing service.

Why can't it track in the background? — Sakib

A web page stops receiving location when the screen locks or the tab is backgrounded. That is a browser rule. A native app would call the same REST API, so the dispatch engine would not change.

Why broadcast instead of assigning one mechanic? — Sakib

It is how real dispatch works, and silent assignment to a mechanic who is away from their phone creates dead requests.

Before you stand up

  • Driver in a normal window, mechanic in an incognito window (both pages share local storage). Log both in beforehand.
  • Run the race test live: ./mvnw -B test -Dtest=AcceptRaceTest (use sh mvnw if the file is not executable).
  • Close the mechanic window mid-job to show the 15-second re-dispatch.
  • Do not demo phone GPS, place search or routing without internet, or the live AI call unless you have tested it with your API key.
  • If map tiles are grey there is no internet. Say tiles come from OpenStreetMap and carry on.
  • Have screenshots or a recording as a backup.
