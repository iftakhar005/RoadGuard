1. Your role in one paragraph

You own the browser side of RoadGuard: the screens a driver and a mechanic actually use, the maps, the live updates that make the screen change without a refresh, and the photo step for AI triage. You also drive the live demo. Ifty owns the server; the two halves meet at the REST API and the WebSocket topics, and you consume what Ifty guarantees.

Honest scope. The frontend is plain HTML, CSS and JavaScript with Leaflet for maps and SockJS plus STOMP for WebSocket. There is no React, no bundler. If asked “why no framework?”: it keeps the project small enough to explain line by line, and the interesting engineering is on the server.

2. What to say: a 2-minute script

Opening (the pitch). “A driver breaks down at night. They press one button, and every qualified mechanic nearby is alerted at the same time. The first to accept gets the job; everyone else is told it is taken.”

What I built. “Everything the user touches. The driver drops a pin, picks the problem, and optionally attaches a photo. The mechanic sees an offer card, taps accept, and then both screens follow the job live on a map with a real road route and an ETA.”

The part I am proudest of. “The screen never lies. If the live connection drops, it shows Reconnecting and keeps polling. If the route service is down, it draws a dashed straight line and labels it as a straight line. If the GPS signal is poor, it holds the last good position instead of jumping.”

Handoff to Ifty. “What happens when I press Accept is Ifty’s part: the lock that makes sure exactly one mechanic wins.”

3. The driver experience

Files: driver.html, driver-sos.js, driver-map.js, sos-radar.js.

Open the page, find the pin The map starts at a fallback of Dhaka (23.8103, 90.4125) and tries the device GPS. The driver can drag the pin to correct it. Say: “Drag the pin to where you are.”
Choose the problem Ten issue types from a dropdown (flat tyre, dead battery, engine, electrical, brakes, out of fuel, overheating, locked out, towing, other) plus an optional note.
Optionally attach a photo JPG, PNG or WEBP up to 5 MB, checked in the browser before upload, with a preview. Details in the photo section.
Press Send SOS POST /api/requests with issue type, coordinates, note and a hasPhoto flag. If there is a photo, it is uploaded as a second call.
The red radar appears SosRadar draws a pulsing red circle at the current search radius. When the server widens the search, the circle grows smoothly and the map re-fits. Say: “That red circle is the kilometres we are searching right now.”
Status text follows the state machine Twelve states, each with plain-language wording, e.g. OFFERED shows “Ringing nearby mechanics”, EN_ROUTE shows “On the way to you”, ESCALATED shows “Still looking”.
The mechanic appears and moves The helper marker glides to each new position, the route is drawn on real roads, and a label shows distance and time. A Cancel request button stays on the status panel until the request is completed or cancelled.

If the driver closes the tab

On load, the page calls GET /api/requests/mine. If a live request exists, it resumes the status screen and polling instead of showing the form again. This is why a refresh does not lose the job.

4. The mechanic experience

Files: mechanic.html, mechanic-console.js, job-map.js, pin-picker.js (mechanic-side pin and place search).

Go on duty A duty toggle calls POST /api/mechanic/status. Going on duty starts GPS following.
Heartbeat every 5 seconds While on duty the page posts the position (or a bare heartbeat if there is no fix yet). This is what lets the server notice a vanished mechanic after 15 seconds. Say: “The server knows I am alive because my browser keeps telling it.”
Offer cards arrive Pushed over WebSocket, with a 15-second polling fallback. Each card shows issue, severity and, if the driver sent one, the photo.
Accept or decline Accept sends the offer token. The response says whether this mechanic won. A loser sees “Someone got there first”. Declining is best effort and the card slides away.
The job stepper On my way → Arrived → Working → Done. Each tap calls POST /api/requests/{id}/status and the server decides whether the move is legal.
Job map JobMap shows the mechanic and the driver with a road route and ETA, re-fetching the route only when needed (see Maps).

GPS filtering (explain this one well)

The page uses the browser’s watchPosition with high accuracy. Each fix goes through two filters:

  • Accuracy over 120 m is ignored and the last good position is kept, with a visible “Weak signal” note.
  • A move under 15 m is treated as jitter and not saved.

Constants in the code: WORST_ACCURACY_M = 120, JITTER_KM = 0.015. This stops a phone on a dashboard from twitching on the driver’s map.

If permission is refused, or the page is not on HTTPS or localhost, the page tells the mechanic to place the pin by hand. Browsers only give location to secure contexts, which the code checks with window.isSecureContext.

5. The real-time client

File: live.js (89 lines). It wraps SockJS and STOMP in a small module called Live.

What it does

  • Connects to /ws with the JWT in the STOMP CONNECT frame (Authorization: Bearer ...)
  • Subscribes to /user/queue/updates (private messages)
  • Subscribes to extra topics like /topic/request/{id} for a specific job
  • Calls every registered handler for each message; one broken handler cannot stop the others
  • Shows a Live or Reconnecting indicator
  • Retries the connection after 3 seconds if it drops

Why polling is still there

  • Driver page polls every 15 s
  • Mechanic page polls every 15 s
  • Driver map refreshes shops every 30 s

WebSocket gives speed; polling gives safety. If a push is lost or the socket is down, the next poll still corrects the screen.

How the driver sees the mechanic move

  1. The mechanic’s page saves a new position to the server.
  2. The server publishes a message of type MOVED to /topic/request/{id}.
  3. The driver’s Live.onMessage handler receives it and moves the marker straight from the message, with no refetch.
  4. Any other message type just triggers a normal poll().
Latency number. The project docs say 4–13 ms. That was measured earlier and I did not re-measure it. Say “a few milliseconds in our earlier measurements”, or re-measure it tonight before you quote a figure.

Libraries: Leaflet 1.9.4 (maps), OpenStreetMap tiles, OSRM (routing), Nominatim (place search). None need an API key.

Route throttling

A mechanic reporting every 5 seconds must not hammer the public routing service. JobMap re-fetches the route only if the job is new, the mechanic moved more than 150 m since the last route (MOVED_KM = 0.15), or the last route is older than 25 s (REFETCH_MS = 25000). Between fetches the marker still moves smoothly.

Good answer if asked about the fallback. “If the router is unreachable the screen still says something true: a dashed straight line, labelled ‘direct line’, with a rougher time estimate. It never pretends a straight line is a road.”
Colour language. The project docs describe blue, green, orange and red meanings. What I could confirm in the code: red is the search radius (#E5484D), the driver-side route line is green (#2E9E5B), the mechanic-side route line is blue (#2F6BFF), and shop markers use an amber/orange style. Check the live screens before you describe a colour for each marker.

7. The photo flow for AI triage (your half)

Server side (parsing, fallback, retries) is Ifty’s. Yours is everything up to the upload and what the mechanic sees.

Choose a photo File input accepts JPG, PNG or WEBP with capture="environment" so phones offer the rear camera. Files over 5 MB are rejected in the browser with a toast, and a preview is shown with a FileReader.
Create the request first POST /api/requests with hasPhoto: true. The server saves the request in the DIAGNOSING state.
Upload the photo second POST /api/requests/{id}/photo as FormData. The button reads “Checking the photo” and the status screen shows “Checking the problem”.
If the photo fails A toast says “The photo could not be read, searching on the problem you picked” and the page loads the request as it stands. The rescue is never blocked by the photo.
The driver sees the result When the server has a diagnosis, the status panel shows a Photo check badge with the fault category, a severity badge and the safety guidance, plus a “Needs” cell with the required specialization. All text is escaped before it goes into the page.
The mechanic sees the photo The offer card contains a placeholder with a photo URL. The page fetches it with the bearer token and shows it through URL.createObjectURL. Why not just an <img src>? Because an image tag cannot send an Authorization header, and the photo is private to the people on the job.
Be honest in the demo. The live model needs an API key and internet. With the default setting (app.ai.provider=stub) the server uses its fallback, so a photo will not give a real diagnosis. Nobody has measured the AI’s accuracy, so make no accuracy claim.

11. Driving the live demo

Before you stand up

  • Driver in a normal window; mechanic in an incognito window. Both pages share local storage, so one will log the other out.
  • Log both in and put the mechanic on duty beforehand. Never do login on stage.
  • Send a fresh SOS rehearsal first, so you know it works on this machine.
  • Have screenshots or a recording ready as a backup.

Internet matters more than the docs say. The pages load Leaflet, SockJS, STOMP and the Inter font from CDNs (cdn.jsdelivr.net, cdnjs.cloudflare.com, Google Fonts), and map tiles come from OpenStreetMap. With no internet the maps and the live connection will not load at all, not just the tiles. Check the venue network, or have a recording ready.

Do not demonstrate

  • Phone GPS: it needs HTTPS, a lit screen and an outdoor signal.
  • Place search or routing without internet.
  • The live AI call, unless you have tested it with an API key.
  • The 80-second radius ladder, unless asked.

If something breaks

  • Grey map tiles: no internet. Say the tiles come from OpenStreetMap and describe what you would see.
  • No offer appears: the mechanic was marked offline. Toggle duty off and on, then send a fresh SOS.
  • Anything odd: send a new SOS. Fresh requests always work.

12. Questions you will probably get

Why not just use Google Maps?

Google Maps shows where things are. It does not decide who gets the job when several mechanics accept at once. The map is a library we call; dispatch is what we built. We use OpenStreetMap and OSRM, which need no API key or billing account.

How does the driver see the mechanic move so fast?

The server publishes each position to that job’s WebSocket topic and the page moves the marker from the message, with no refetch. The route and ETA are throttled separately (150 m or 25 s) so we do not hammer the routing service.

Why can it not track in the background?

A web page stops receiving location when the screen locks or the tab is backgrounded. That is a browser rule, not a flaw in our code. A native app would call the same REST API, so the dispatch engine would not change.

Why keep polling if you have WebSocket?

WebSocket is fast but can drop. Polling every 15 seconds is the safety net: if a push is lost, the next poll still corrects the screen.

How do you stop a jittery GPS from making the marker twitch?

Two filters: fixes worse than 120 m accuracy are ignored, and moves under 15 m are treated as noise.

What if the routing service is down?

We draw a dashed straight line, label it “direct line”, and estimate time from an average city speed, so the screen still says something true.

Is the 5 MB limit secure?

The browser check is a convenience. The server enforces the real limit and the allowed types (JPG, PNG, WEBP), and guards against paths that escape the uploads folder.

Why no React or other framework?

To keep it small enough to explain line by line and to avoid a build step. The hard engineering is on the server. For a larger product we would reconsider.

Where is the admin dashboard?

Not built. admin.html is a placeholder. Say so plainly.

Could someone read another driver’s request?

That is enforced on the server (JWT and role checks), which is Ifty’s area. From the client side, pages redirect by role, but the redirect is only for convenience, not security. Hand this one to Ifty.

13. Limits you should say out loud

  • Location sharing needs HTTPS (or localhost), a lit screen and a decent signal.
  • No background tracking in a browser.
  • The app depends on CDNs and public OpenStreetMap services, so it needs internet. Public Nominatim and OSRM servers are shared services, not guaranteed for heavy use.
  • The admin page, ratings UI and event replay are not built.
  • I did not run the app in a browser to write this page. Everything here is from reading the code, so click through each screen before you present.
