1. How I start

Sir, in RoadGuard I did the part of everything the user sees. That is the driver’s screen, the mechanic’s screen, the maps, the live connection that keeps those screens up to date, and the shop and skills pages. I also worked on the photo step of the AI fault check, and I will run the live demo.

My friend Ifty did the backend: the dispatch engine, the matching, the rule that only one mechanic can win a job, the security and the tests. Our two parts meet at the REST API and the WebSocket. He provides the endpoints, and my pages call them.

I will now go through my part area by area, and say what each file is for.

About the API. The docs give Sakib the browser side, the shop service on the server (ShopService.java) and the use of the API. The API controllers themselves are listed under Ifty’s backend. So say “my pages use the API”, not “I wrote the API”, unless you really did write the controllers. If you did, tell me and I will add them.

2. The driver experience

First, the driver side. A driver opens one page, sees a map, drops a pin where they are, says what the problem is, and presses Send SOS. After that the same panel shows the live status of the request until it is finished.

FileLinesWhat it is about
driver.html102The driver’s page. It holds the top bar (“Driver Portal”), the map and the side panel, and loads all the scripts the driver needs.
driver-sos.js381The SOS panel. First it shows the form: your location, the problem (ten choices such as flat tyre, dead battery, engine, brakes, towing), an optional note and an optional photo, then the Send SOS button. After sending, it shows the request number, a plain-language status (“Looking for a mechanic”, “On the way to you”, “All done”), the assigned mechanic, the search radius and a Cancel request button. If the driver refreshes the page, it picks the open request back up.
driver-map.js294The driver’s map. It shows the driver’s draggable pin, finds the driver’s position from the device, shows nearby repair shops as markers, and once a mechanic accepts, shows the mechanic moving towards the driver with the distance and time.

3. The mechanic console

Second, the mechanic side. A mechanic goes on duty, receives job offers as cards, accepts one, and then moves the job forward step by step until it is done.

FileLinesWhat it is about
mechanic.html265The mechanic’s page, built from cards: the duty switch (Off duty / On duty), a map for the mechanic’s own location, What I can fix (skills), My shop, the current job with its map, and the list of offers.
mechanic-console.js576The behaviour of that page. It turns duty on and off, follows the mechanic’s location from the device and keeps telling the server the mechanic is still there, shows each offer as a card with Accept and Decline, says whether the mechanic got the job or “someone got there first”, and shows the job steps: On my way, Arrived, Working, Done.

4. Maps and location

Third, the maps. All maps use Leaflet with OpenStreetMap, so we do not need a paid map key. I wrote four small files for the map features.

FileLinesWhat it is about
sos-radar.js138The red pulsing circle that shows how far we are searching. When the search widens, the circle grows.
pin-picker.js270Lets the mechanic set a location by dragging a pin, searching a place name, using the device location or typing coordinates. Used for the mechanic’s own position and for the shop position.
route.js67Gets the road route, distance and time between two points from OSRM. If that service is not reachable, it draws a straight line instead and says so.
job-map.js139The mechanic’s map for the current job: the mechanic, the breakdown location, the route and the time to get there.

5. The live connection

Fourth, the live connection. Screens should change without the user pressing refresh, so I wrote a small file that listens to the server and tells the page when something changes.

FileLinesWhat it is about
live.js89Opens the WebSocket connection to the server, logs in with the user’s token, listens to that user’s updates and to the updates of one request, and passes each message to the page. It shows a small Live or Reconnecting indicator and tries to reconnect by itself. The pages also check the server every 15 seconds as a backup.

6. Shops and skills

Fifth, shops and skills. A mechanic can say what jobs they can do and register a shop with a name, a type, a phone number, an address, a location on the map and a photo. Drivers then see these shops on their map.

FileLinesWhat it is about
mechanic-shop.js164The My shop form on the mechanic page: shop details, a pin for the shop location, and the shop photo with a preview. It stops files over 5 MB before sending.
mechanic-skills.js105The What I can fix picker. The mechanic ticks skills and presses Save skills. These skills decide which jobs the mechanic is offered.
ShopService.java189The server side of shops. It saves and reads a mechanic’s shop details, returns the list of all shops for the driver’s map, and stores and returns the shop photo. It accepts only JPG, PNG or WEBP, deletes the old photo when a new one is uploaded, and keeps the file inside the uploads folder.

7. The photo step of the AI check (my side)

Sixth, the photo step. On the SOS form the driver can add a photo. My page sends the photo to the server, which asks the AI to work out the fault. The driver then sees the result, the fault type, how serious it is and a safety tip, and the mechanic sees the photo on the offer card. The AI itself, and what happens if it fails, is Ifty’s part.

Files: driver-sos.js (photo option, preview, upload, result block on the status panel) and mechanic-console.js (loading the photo on the offer card).

10. The API my pages use

My pages talk to the server through the REST API. They ask the server for data and send actions, for example create a request, accept an offer or save my shop. Updates that arrive on their own come through the WebSocket.

What my pages doCalls
Sign in, register, who am I, reset password/api/auth/login, register, me, forgot-password, reset-password
Driver sends and follows an SOS/api/requests (create), /api/requests/mine, /api/requests/{id}, /cancel, /photo
Driver sees shops/api/shops
Mechanic on duty, location, skills/api/mechanic/me, status, location, heartbeat, skills
Mechanic shop and shop photo/api/mechanic/shop, /api/mechanic/shop/image
Mechanic offers and jobs/api/mechanic/offers, /api/requests/{id}/accept, /decline, /status, /api/requests/mine-assigned
Live updatesWebSocket /ws, listening to /user/queue/updates and /topic/request/{id}

This list comes from the calls found in the JavaScript files. The server code behind each call is Ifty’s part.

11. The demo I will run

Finally, I will run the live demo. A driver sends an SOS, the mechanic receives the offer and accepts it, the driver sees the mechanic coming on the map, and the mechanic moves the job through the steps. Then Ifty will show the test that proves only one mechanic can win a job.

  • Driver in a normal browser window, mechanic in a private (incognito) window. Both pages share the same browser storage, so using one window would log the other out.
  • Log in and put the mechanic on duty before you start.
  • The pages need the internet: Leaflet, the live-connection libraries and the fonts load from the web, and the map tiles come from OpenStreetMap. Without internet the maps and live updates will not load, so keep a recording as a backup.
  • If no offer appears, the mechanic is probably off duty. Switch duty off and on, then send a new SOS.
